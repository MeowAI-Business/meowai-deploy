# Downstream Repair Runbook

`repair` is for reconciling a managed deployment whose runtime state no longer
matches its registration or approved release. It is not a replacement for
`upgrade`, `rollback`, or `clean`.

## Safety boundary

- The source can only select from the predefined typed actions; the CLI
  executes locally implemented handlers and never runs source-provided shell,
  file paths, or Docker arguments.
- Repair never runs `docker compose down -v` or `--remove-orphans`; unknown
  services, containers, volumes, networks, or mounts stop the plan as a
  manual boundary instead of being deleted.
- B0 only observes or restarts managed services.
- B1 snapshots managed env, Compose, updater, `data/state.json`, systemd
  entries (including owner/mode), named-volume labels/source fingerprints, and
  persistent mount identity.
- B2 adds PostgreSQL, Redis, and data inventory backups before a structural
  release. A failed B2 backup stops the release before it can change services.
- `--allow-data-migration` authorizes only the signed manifest's declared data
  migration. It does not bypass signature, artifact allowlist, compatibility,
  or backup checks.

The source `CRYPTO_SECRET` and the database must be backed up together. If an
old key is gone, installation credentials can be rotated, but provider,
channel, or user ciphertext is reported as `DATA_ENCRYPTED_WITH_LOST_KEY` and
must be handled manually.

## Execution and recovery

1. Run `meowai-deploy repair --check` and review the diagnostic codes.
2. Run `meowai-deploy repair --plan --json`; retain the plan fingerprint.
3. Apply with `--yes --plan-fingerprint <fingerprint>` and add
   `--allow-data-migration` only for an explicitly approved migration.
4. A pre-activation failure restores the previous target env and aborts the
   pending operation. After activation, the new credentials remain in place;
   do not restore the old env.
5. `failed_recoverable` preserves the journal and backup. Re-run the same plan
   to resume reporting/probe verification. `operation_aborted` is valid only
   before activation. `PERSISTENT_RESOURCE_IDENTITY_CHANGED`, dependency
   health failures, and unknown Compose resources require manual handling.

Heartbeat/reporting and public endpoint probing are independent checks. A
successful credential activation with a failed public probe is reported as
`succeeded_with_warning`, not rolled back.

Before activation the CLI asks the protected updater socket or signed target
agent binary for a one-time challenge proof using the updater credential,
nonce, and operation identity. The proof must be generated by target-side
managed code; an older agent that lacks this capability cannot be used for
credential activation and the operation stops for agent repair/manual
handling. After activation, report triggering remains compatibility-aware: the
CLI polls normal heartbeat/snapshot state when the protected report endpoint is
unsupported.
